## 2) الاستحقاق عند انتهاء `paid_through` (خادمي)

مرجع الوقت: ساعة الخادم فقط — حقل `paid_through` (timestamptz).

| القدرة | `now() < paid_through` + استحقاق حي + عضوية | `now() >= paid_through` (انتهاء) |
| --- | --- | --- |
| دخول | نعم | **نعم** (عضوية سارية) |
| قراءة محادثات / تصدير | حسب ACCESS | **نعم** حسب ACCESS |
| تجديد / عرض الاشتراك | مالك الشركة (§6) | **نعم** |
| AI / أتمتة | نعم إن entitlement يسمح | **لا** |
| إرسال يدوي عبر فيلورا | نعم إن مسموح | **لا** |
| تعديل معرفة | مالك + حدود تخزين موجودة | **نعم محليًا** ضمن حدود التخزين؛ خطوات مدفوعة محجوبة (§5) |

### تعريف «منتهٍ» مقابل «لم يدفع أصلًا»
| حالة | معنى | نافذة وارد 7 أيام؟ | حالة اشتراك B |
| --- | --- | --- | --- |
| `paid_through` قيمة سابقة و`now() >= paid_through` | اشتراك **منتهٍ** | **نعم** (من لحظة الانتهاء) | `ended` (أو ما يعادله) |
| لم يدفع قط / `paid_through IS NULL` | **ليس** اشتراكًا منتهيًا | **لا** — لا تُمنح النافذة تلقائيًا | `unprovisioned` أو `awaiting_payment` — **ليس** `ended` |

### التجديد المبكر
عند دفع تجديد ناجح قبل انتهاء الفترة:  
`paid_through_new = max(now(), paid_through_current) + period_duration`  
أي تُحفظ المدة المتبقية ثم تُضاف مدة الفترة الجديدة. لا تصفير للفترة السارية.

### أولوية التعطيل (لا تُعاد)
1. تعليق أمني للشركة أو سحب/إيقاف العضوية.  
2. ثم انتهاء `paid_through` / إيقاف الاستحقاق.  
3. اشتراك مدفوع لا يتجاوز (1).

### الإلغاء
- `cancel_at_period_end`: لا يقطع الفترة المدفوعة؛ التشغيل يستمر حتى `paid_through`.  
- بعده: نفس عمود الانتهاء أعلاه.

### فحص الاستحقاق (لا يعتمد على cron وحده)
يُقيَّم الاستحقاق عند **كل تنفيذ** ذي صلة: إرسال يدوي/آلي، AI/أتمتة، حفظ وارد، وأي بوابة مدفوعة.  
Cron/مهام خلفية **مساعدة للعرض/التنبيه فقط** — ليست مصدر الحقيقة الوحيد للقطع.

## 3) نافذة حفظ الوارد بعد الانتهاء

| معامل | قرار |
| --- | --- |
| المدة | **7 أيام** بعد `paid_through` **فقط** لحساب كان له `paid_through` ثم انتهى (§2) |
| الحد | سقف بيانات/رسائل **قابل للتهيئة** (خادمي) — القيمة الفعلية تُضبط عند التنفيذ من إعداد موجود أو config صريح؛ **لا اختلاق رقم تجاري هنا** |
| بعد انتهاء النافذة أو بلوغ الحد | **لا** تخزين محتوى وارد جديد · **لا** إنشاء jobs له |

### ناتج مسار الوارد (ثلاثي صريح — لا خلط)

| الناتج | المعنى | استجابة للمزوّد/القناة | تسجيل |
| --- | --- | --- | --- |
| `stored` | حُفظ المحتوى فعليًا | نجاح معالجة عادي | سجل حفظ ناجح فقط إذا حُفظ |
| `rejected_by_policy` | مرفوض بسياسة (انتهاء/حد/غير مؤهل) | اعتراف ناجح يمنع **عاصفة retries** (ليس 5xx متكرر) | قرار سياسة فقط — **ممنوع** تسجيله كحفظ ناجح |
| `retryable_failure` | فشل بنيوي/DB لرسالة كانت مؤهلة | فشل قابل لإعادة المحاولة | لا ادّعاء حفظ |

رمز قرار سياسة مقترح: `inbound_rejected_unpaid_retention` (أو ما يعادله) — بلا ادّعاء أن الرسالة محفوظة.

### فصل المسارات بعد الانتهاء
| مسار | مسموح؟ |
| --- | --- |
| معالجة **delivery statuses** لرسائل/محاولات قائمة | نعم (تسوية حالة) |
| تسوية محاولات إرسال **قديمة** | نعم (لا إنشاء إرسال جديد) |
| إنشاء إرسال جديد (يدوي/آلي) عبر فيلورا | **لا** بعد `paid_through` |
| إنشاء job إجابة/وارد جديد خارج نافذة 7 أيام أو فوق الحد | **لا** |

### حدود الاستخدام والتخزين (إغلاق فجوة)
- **غياب حد استخدام مطلوب** لعملية ما ⇒ **تُمنع تلك العملية** (fail-closed) مع رسالة نقص صريحة — لا افتراض حد.
- حدود **حجم/نوع الملف الواحد** ≠ حصة تخزين للشركة ولا حصة باقة اشتراك.
- **لا اختلاق** حصص تخزين باقات ولا أسعار في المنتج.
- قيم اصطناعية (حدود/أسعار اختبار) **مسموحة فقط** داخل اختبارات معزولة ومعلَّمة صراحة — لا تتسرب لإعدادات تشغيل.

## 5) المعرفة بعد الانتهاء — محلي vs مدفوع

**مالك الشركة** يعدّل المعرفة ضمن حدود التخزين الموجودة.

| خطوة | تصنيف |
| --- | --- |
| إنشاء/تعديل نص معرفة، بيانات وصفية، اعتماد/إلغاء اعتماد للإجابة | **محلية** (خادم فيلورا) — مسموحة بعد الانتهاء ضمن الحدود |
| رفع ملف إلى التخزين الحالي للشركة ضمن الحصص الموجودة | **محلية** للمسار الحالي — مسموحة إن الحصة موجودة؛ وإلا رفض صادق |
| استخراج/فهرسة تستدعي مزوّد AI مدفوعًا | **مدفوعة** — **محجوبة** بعد الانتهاء |
| `ask` / إجابة حية / أي استدعاء مزوّد إجابة | **مدفوعة** — **محجوبة** |
| إرسال واتساب عبر فيلورا | **مدفوع/تشغيلي مدفوع** — **محجوب** بعد الانتهاء (§2) |

## 7) عقد Paymob الفعلي (من الوثائق الرسمية فقط)

### 7.1 إنشاء الدفع — Create Intention
- **Auth:** رأس `Authorization: Token <secret_key>` (Secret Key من لوحة المزوّد؛ Test/Live حسب الوضع).
- **مدخلات موثّقة مطلوبة/مهمة:**
  - `amount` (number) — إجمالي المعاملة **بالـ cents** حسب الوثيقة
  - `currency` (string) — يجب أن تطابق عملة Integration ID
  - `payment_methods` (array) — Integration ID(s)؛ الحالة Test/Live يجب أن تطابق المفتاح
  - `items[]` — لكل عنصر `name` و`amount` مطلوبان
  - `billing_data.phone_number` — مطلوب
  - `special_reference` — مرجع تاجر فريد؛ يعود في الـ callback تحت `merchant_order_id`
  - `notification_url` — POST بتفاصيل المعاملة بعد النجاح/الفشل (مدعوم مع card Integration IDs حسب الوثيقة)
  - `redirection_url` — إعادة توجيه العميل بعد الإكمال (Card/Wallet حسب الوثيقة) — **للعرض فقط**
- **مخرجات ارتباط مهمة:**
  - `client_secret` — لفتح Unified Checkout / Pixel
  - `intention_order_id` / Order ID — للربط مع callback
  - Intention ID
  - `special_reference` مُعاد

### 7.2 مصدر الحقيقة vs إعادة التوجيه
| قناة | نوع | الاستخدام في فيلورا |
| --- | --- | --- |
| Transaction Processed Callback | POST JSON خادمي | **مصدر الحقيقة** لتحديث حالة الدفع/الاستحقاق |
| Transaction Response Callback | GET query للعميل | عرض رسالة للمستخدم فقط — **ممنوع** الاعتماد عليه لتفعيل اشتراك |

### 7.3 التوقيع والتحقق الخادمي (HMAC)
من [HMAC Transaction Callback](https://developers.paymob.com/paymob-docs/developers/webhook-callbacks-and-hmac/hmac/hmac-transaction-callback):
1. ترتيب مفاتيح السلسلة (lexicographic كما وثّقته Paymob — القائمة الثابتة أدناه).
2. دمج **قيم** الحقول بلا فاصل.
3. `HMAC-SHA512` بمفتاح HMAC Secret من لوحة المزوّد.
4. مقارنة الناتج مع معامل الاستعلام `hmac`.

مفاتيح السلسلة الموثّقة (Processed POST من `obj`؛ Response GET بأسماء مسطّحة حيث ذُكر الفرق):

`amount_cents` · `created_at` · `currency` · `error_occured` · `has_parent_transaction` · `id` (POST: `obj.id`) · `integration_id` · `is_3d_secure` · `is_auth` · `is_capture` · `is_refunded` · `is_standalone_payment` · `is_voided` · `order.id` (GET: `order_id`) · `owner` · `pending` · `source_data.pan` · `source_data.sub_type` · `source_data.type` · `success`

**عائق صريح إن ظهر لاحقًا:** تمثيل قيمة `null` في السلسلة غير موضّح رسميًا في الصفحة أعلاه — يُثبَّت من حمولة اختبار حقيقية قبل الاعتماد الإنتاجي، بلا تخمين لغة.

### 7.4 حالات المعاملة (من حقول الـ callback الموثّقة — ليست أسماء Thawani)
لا تُخترع أسماء حالة مزوّد. تُقرأ الحقول البوليانية/الرقمية الموثّقة على `obj`:

| ملاحظة موثّقة | دلالة تشغيلية في فيلورا (طبقة A داخلية) |
| --- | --- |
| `success` true/false | نجاح/فشل المعاملة |
| `pending` | معلّق/غير مكتمل بعد |
| `error_occured` | خطأ أثناء المعالجة |
| `is_voided` / `is_refunded` / `is_captured` + مبالغ مرتبطة | عمليات لاحقة — لا تُفعَّل فترة تلقائيًا بلا قواعد لاحقة معتمدة |
| `id` | معرّف معاملة Paymob (مفتاح منع تكرار الحدث) |
| `order.id` | Order ID للربط |
| `order.merchant_order_id` | = `special_reference` إن أُرسل |
| `amount_cents` · `currency` | للمطابقة مع الطلب المقفول |
| `integration_id` · `is_live` | مطابقة حساب المزوّد والبيئة |

تعيين داخلي مقترح (طبقة A فيلورا — ليست أسماء Paymob):  
`intent_created` → `provider_submitted` → `paid` | `failed` | `unresolved` (+ `refunded*` / `disputed` لاحقًا بمراجعة بشرية).

### 7.5 تثبيت الطلب قبل الإرسال إلى المزوّد
قبل أي نداء Create Intention يُقفل في سجل العملية ولا يُغيَّر بعد الإرسال:
- `company_id`
- `plan_version_id` (إصدار الباقة)
- `amount` (وحدة المزوّد بعد تثبيت عامل التحويل)
- `currency` (= `OMR`)
- `period_duration`
- حساب المزوّد / `integration_id`(s)
- البيئة `test|live`
- `special_reference` / `client_op_id` (+ بصمة مدخلات)

### 7.6 الاستعلام والمصالحة ومنع التكرار
| بند | قرار العقد |
| --- | --- |
| تفعيل الاستحقاق | فقط بعد تحقق خادمي: HMAC · مبلغ · عملة · هوية طلب/`special_reference` · شركة · Integration/حساب · `test|live` · `success` وليس `pending` |
| منع تكرار الحدث | قيد فريد على معرّف معاملة المزوّد `obj.id` (+ لا فترة مزدوجة لنفس العملية الناجحة) |
| منع تكرار العملية | مستويان: `client_op_id`+بصمة · هوية شراء/تجديد واحدة عبر التبويبات |
| انقطاع بعد الإرسال | العملية `unresolved` + مصالحة لاحقة ≠ تحصيل جديد |
| تحصيلان حقيقيان | تسجيل + مراجعة بشرية · لا فترة مزدوجة تلقائيًا |
| استعلام/Retrieve API | **عائق صريح** إن لم تُوثَّق صفحة استعلام معتمدة في مصادر هذا العقد قبل التنفيذ — لا افتراض مسار استعلام من Thawani أو من ذاكرة تدريب |

### 7.7 الاشتراكات التلقائية (مؤجّلة)
Create Subscription plan يتطلّب: Bearer auth token · `frequency` ∈ {7,15,30,60,90,180,360} · `integration` = MIGS Moto · `webhook_url` على مستوى الخطة.  
**v1 لا يستخدمه** حتى تأكيد تفعيل الاشتراكات التلقائية لحساب Paymob عُمان.

### 7.8 Adapter (Paymob Test — Hosted Checkout)
```
createIntention(lockedOrder) → client_secret + intention/order ids + special_reference
openHostedCheckout(client_secret) → Unified Checkout redirect
verifyProcessedCallback(hmac, obj) → accept|reject
mapTransaction(obj) → canonical A-layer event (paid|failed|pending|…)
reconcileUnresolved(op) → يحتاج API استعلام موثّق أو أداة لوحة — وإلا يبقى عائقًا
createRefund(...) → فقط بعد قرار بشري لاحق؛ ليس في دفعة v1 الأولى
```
لا أسرار بالمتصفح · لا تخزين بطاقات · لا live قبل اعتماد §1/§G.

### 7.9 استرداد / اعتراض / تفعيل تجريبي
- استحقاق استرداد العميل: **مراجعة يدوية** فقط.
- قدرة استرداد المزوّد ≠ حق العميل.
- تفعيل تجريبي: بيئة Test منفصلة فقط؛ مؤقت · مدقّق · لا إيراد وهمي إنتاجي.

## 9) اللوحات (مصادر خادمية)

### عميل `/app`
حالة الاشتراك · `paid_through` · نافذة الوارد المتبقية **إن** انتهت فترة مدفوعة سابقًا · الاستخدام فقط إن وُجد قياس فعلي · ما توقف وسببه · عمليات معلّقة · تجديد يدوي لمالك الشركة.  
ممنوع: عدّادات وهمية · `companies.active` = مدفوع · زر يزوّر paid · منح نافذة 7 أيام لـ `paid_through IS NULL`.

### أدمن `/admin` ضمن ACCESS الحالي
حالات الاشتراك في النطاق · عمليات `unresolved`/تحصيلان للمراجعة.  
لا صلاحية مالية تلقائية للمفوّض/الموظف.

## T) مصفوفة الاختبارات (في هذه الوثيقة)

| ID | السيناريو | المتوقع |
| --- | --- | --- |
| T1 | شركتان معزولتان — عملية/webhook لـ A | لا تغيّر اشتراك B |
| T2 | تكرار `client_op_id`+بصمة | نية واحدة |
| T3 | تبويبان متزامنان لنفس الشراء | هوية شراء واحدة |
| T4 | انقطاع بعد Create Intention | `unresolved` بلا تحصيل مزدوج |
| T5 | HMAC مزوّر/ناقص | رفض · لا تفعيل |
| T6 | مبلغ أو عملة لا تطابق الطلب المقفول | لا `paid_through` جديد |
| T7 | `paid_through IS NULL` (لم يدفع) | ليس `ended` · بلا نافذة 7 أيام · بلا AI/إرسال |
| T8 | عبور `now() >= paid_through` | قطع AI/إرسال · بقاء دخول/قراءة/تصدير |
| T9 | تجديد مبكر مع متبقٍ | المتبقي + المدة الجديدة |
| T10 | وارد داخل نافذة 7 أيام بعد انتهاء حقيقي | `stored` إن تحت الحد |
| T11 | وارد بعد النافذة/فوق الحد | `rejected_by_policy` · بلا سجل حفظ ناجح · بلا retry storm |
| T12 | فشل DB لوارد مؤهل | `retryable_failure` |
| T13 | غياب حد استخدام مطلوب لعملية | العملية ممنوعة |
| T14 | حد ملف واحد ≠ حصة شركة | لا يُعامل كحصة اشتراك |
| T15 | قيم اصطناعية | فقط في اختبارات معزولة معلَّمة |
| T16 | `redirection_url` success بلا callback موثّق | لا تفعيل |
| T17 | `success=false` أو `pending=true` | لا `paid` / لا تمديد |
| T18 | استحقاق عند الإرسال لا عبر cron فقط | بوابة التنفيذ ترفض بعد الانتهاء حتى دون تشغيل cron |

**دفعة التنفيذ الأولى المستقلة (§P مرحلة 1):** تغطي منطق T7–T9 وT13–T15 وT18 محليًا **بدون** مفاتيح Paymob ولا اتصالات دفع. بقية البنود بعد Adapter Test.

## P) خطة التنفيذ المرتبة (للمراجعة — بلا بدء كود)

### المرحلة 0 — اعتماد بشري (مانع قبل كل شيء)
| اعتماد | يمنع |
| --- | --- |
| مراجعة هذا العقد + الخطة | أي هجرة/كود فوترة |
| هوية تاجر Paymob عُمان + قبول الحساب البنكي/التسوية + الرسوم النهائية من Paymob + أسعار + شروط البيع | **تحصيل حي** |
| مفاتيح Test + HMAC Secret + Integration ID(s) في سرّ خادمي | **اختبار Hosted Checkout** |
| تثبيت عامل تحويل OMR↔`amount`/`amount_cents` من مصدر Paymob عُمان موثّق | أي إرسال مبلغ |
| توثيق/اعتماد مسار استعلام مصالحة إن لزم | إغلاق `unresolved` آليًا |
| قيم تهيئة: سقف وارد ما بعد الانتهاء · نص التنبيهات 90 يومًا | إكمال اختبارات الاحتفاظ/الوارد |

**دليل قبول 0:** وثيقة معتمدة مكتوبًا؛ قائمة نواقص §G مفتوحة أو مغلقة صراحة.

---

### المرحلة 1 — أول دفعة تنفيذ مستقلة: البيانات + الحالات + الاستحقاق (بلا دفع)
**ينجز:** جداول منطقية `plan`/`plan_version` · `subscription` (`paid_through`, حالات B مع قاعدة NULL≠ended) · `billing_operation` (حقول القفل §7.5) · `billing_webhook_inbox` · فصل مدد حفظ الدفع عن المحادثات · RPC انتقالات خادمية · اشتقاق C وفحصه عند بوابات التنفيذ/الإرسال · نافذة وارد + نواتج ثلاثية · اختبارات محلية T7–T9,T13–T15,T18.  
**اعتمادية:** المرحلة 0 (اعتماد العقد فقط — **بدون** مفاتيح Paymob).  
**دليل قبول 1:**
- `paid_through IS NULL` ≠ `ended` ولا نافذة 7 أيام.
- فشل تجديد منطقي لا يمحو `paid_through` الساري.
- `cancel_at_period_end` يبقي الاستحقاق حتى `paid_through`.
- `now() >= paid_through` ⇒ انتهى تشغيليًا عند بوابة التنفيذ دون المتصفح ودون الاعتماد على cron وحده.
- التجديد المبكر يحتفظ بالمتبقي (اختبار وحدة/SQL محلي بزمن ثابت).
- رفض السياسة ≠ حفظ ناجح.
- لا أسعار/مفاتيح/نداءات مزوّد في هذه المرحلة.

---

### المرحلة 2 — بوابة الاستحقاق والقياس (ربط السطوح)
**ينجز:** ربط بوابات AI/أتمتة/إرسال يدوي عبر فيلورا؛ رفض وارد متعمّد؛ فصل statuses/تسوية قديمة؛ معرفة: محلي مسموح / مدفوع محجوب.  
**اعتمادية:** المرحلة 1.  
**دليل قبول 2:** T8,T10–T12,T18 على السطوح الحقيقية محليًا/اختبارًا بلا دفع.

---

### المرحلة 3 — لوحتا العميل والأدمن
**ينجز:** مصادر خادمية صادقة على `/app`؛ قسم حالات/غير محسوم على `/admin`؛ تنبيهات 90 يومًا + تصدير؛ الحذف النهائي DISABLED.  
**اعتمادية:** المرحلة 2 (قراءة الحالة على الأقل).  
**دليل قبول 3:** لا عدّادات وهمية؛ نواقص القياس/الأسعار صريحة؛ مالك الشركة فقط للمالية.

---

### المرحلة 4 — محوّل Paymob Test (Hosted Checkout)
**ينجز:** Adapter §7 على Test؛ حفظ نية مقفولة قبل النداء؛ Unified Checkout؛ webhook+HMAC؛ تجديد يدوي؛ استرداد لاحقًا خلف مراجعة فقط.  
**اعتمادية:** المرحلة 1 + إغلاق عوائق المفاتيح/عامل OMR/مسار المصالحة اللازم من مرحلة 0.  
**دليل قبول 4:** T1–T6,T16,T17؛ لا live؛ لا تفعيل من redirect وحده.

---

### المرحلة 5 — اختبارات التزامن والتكرار والانقطاع والعزل والانتهاء والتجديد
**ينجز:** إكمال مصفوفة §T على بيئة Test.  
**اعتمادية:** المراحل 2–4.  
**دليل قبول 5:** كل بنود §T بلون أخضر موثّق؛ بلا إيراد وهمي إنتاجي.

## G) ما يمنع الاختبار أو التحصيل الحقيقي تحديدًا

| الهدف | المانع المحدد الآن |
| --- | --- |
| **اختبار Hosted Checkout (Test)** | غياب مفاتيح Test + HMAC + Integration ID في سرّ خادمي؛ عدم اعتماد العقد؛ عدم وجود جداول عمليات؛ **عامل تحويل OMR↔cents غير مثبت من وثيقة عُمان**؛ Hub عُمان/الصفحة الإقليمية أعادت 403 عند الجلب |
| **تحصيل حقيقي (live)** | عدم اعتماد هوية التاجر + قبول الحساب البنكي/التسوية من Paymob + الرسوم النهائية من Paymob + الأسعار + شروط البيع؛ v1 متعمّد على Test أولًا |
| **مصالحة `unresolved` عبر API** | مسار Retrieve/Inquiry غير مدرج بمصدر معتمد في هذا العقد → عائق حتى التوثيق |
| **اشتراكات تلقائية** | مؤجّلة حتى تأكيد تفعيلها للحساب (Moto + Create Subscription plan) |
| **إظهار أسعار للعميل** | الأسعار يحددها مالك المنصة لاحقًا |
| **حدود باقة تخزين/رسائل اشتراك** | لا كتالوج حدود اشتراك في الكود — غياب الحد المطلوب يمنع العملية؛ لا يُختلق |
| **حذف نهائي بعد 90 يومًا** | DISABLED حتى آلية حذف + سياسة خصوصية |
| **استرداد للعميل كحق** | مراجعة يدوية فقط |
| **تمثيل null في HMAC** | غير موثّق صراحة → يُثبَّت من حمولة Test قبل الإنتاج |
| **تعديل ACCESS/LEADS/المحادثات** | خارج نطاق إعداد هذه الوثيقة |

## D) المتبقي بعد الحسم (تشغيل/اعتماد — ليس إعادة فتح السياسة)
