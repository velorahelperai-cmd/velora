## 0) وحدة العميل المحتمل

- الصف التشغيلي = صف `whatsapp_conversations` لشركة واحدة + ربط رقم نشاط واتساب الخاص بتلك الشركة.
- نفس الشخص على رقمين/شركتين = محادثتان منفصلتان في العدّ والقوائم.
- كل عدّاد = `count(conversations)` بنفس فلتر القائمة ونطاق الوصول — **لا** `count(distinct phone/person)`.

## 3) أعمدة على المحادثة

| العمود | قواعد |
| --- | --- |
| `lead_stage` | check بالقيم اليدوية أعلاه فقط (بدون `subscribed`) |
| `lead_stage_reason` | إلزامي عند `trial_or_quote_requested` و`closed_no_subscribe` |
| `internal_note` | داخلي |
| `follow_up_status` | `none` · `scheduled` · `completed` · `cancelled` |
| `follow_up_at` | timestamptz UTC؛ **إلزامي وغير null** عندما `status = scheduled`؛ عند `completed`/`cancelled` يُحتفظ بآخر تاريخ كسجل |
| `last_touch_at` | timestamptz UTC؛ يتبع عقد §4 فقط |
| `lead_revision` | int؛ يزيد مع تحديثات المرحلة/الملاحظة/الموعد فقط |
| `assigned_to` / `control_revision` | موجودان؛ لا تلمسهما RPC المرحلة |

### دورة الموعد
| حالة | قائمة نشطة؟ | التاريخ |
| --- | --- | --- |
| `none` | لا | null |
| `scheduled` | نعم (اليوم / المتأخر) | إلزامي |
| `completed` | لا | محفوظ كسجل |
| `cancelled` | لا | محفوظ كسجل |

إعادة الجدولة من مكتمل/ملغى → `scheduled` + تاريخ جديد. تغيير المرحلة لا يحرّك الموعد تلقائيًا.

## 4) عقد احتساب الرد و`last_touch_at` (نهائي v1)

### 4.1 قبول المزود ≠ تسليم
| الحالة | المعنى في المنتج |
| --- | --- |
| `accepted` / `sent` | المزود قبل الطلب / أُرسل للشبكة — **ليست** «وُصلت للعميل» |
| `delivered` / `read` | تسليم/قراءة على جهاز العميل |
| `failed` | فشل (ابتدائي أو لاحق) |

**قاعدة عرض:** لا تُعرض `accepted` (أو `sent`) كـ`delivered`. شارات التسليم تتبع الحالة الفعلية فقط.

### 4.2 ما يعدّ «رد موظف» لأغراض قائمة الانتظار و`last_touch_at`
رسالة صادرة `sender_kind = staff` (أو المكافئ الحالي) و`delivery_state ∈ {accepted, sent, delivered, read}`.

**لا يُحتسب:**
- assistant (أي حالة)
- نية/claim مرفوض أو غير مقبول
- `failed` (ابتدائي أو بعد قبول سابق)

### 4.3 قائمة «بانتظار رد الموظف»
المحادثة ضمن نطاق الوصول، و`status ≠ resolved`، وآخر رسالة **واردة من العميل** أحدث زمنيًا من آخر رسالة **موظف محتسبة** حسب §4.2 (أو لا توجد رسالة موظف محتسبة بعد آخر وارد).

- رد المساعد **لا يخرج** المحادثة من هذه القائمة.
- الاسم في UI والقوائم: **بانتظار رد الموظف** فقط (لا «بلا رد»).

### 4.4 أثر فشل التسليم اللاحق
إذا كانت رسالة موظف محتسبة ثم أصبحت `failed`:
1. تسقط فورًا من مجموعة الرسائل المحتسبة (§4.2).
2. إن عاد الشرط في §4.3 متحققًا → المحادثة **تعود** إلى «بانتظار رد الموظف».
3. `last_touch_at` **لا يُنقص** عند الفشل (انظر §4.5).

### 4.5 تحديث `last_touch_at` (وقت الحدث + منع الرجوع)
عند انتقال رسالة موظف إلى حالة محتسبة (§4.2) لأول مرة في دورة حياتها:

```
last_touch_at := GREATEST(last_touch_at, message_event_at)
```

- `message_event_at` = وقت حدث الرسالة المعتمد للصف (مثل `received_at` / وقت حدث التسليم المخزَّن) — **ليس** `now()` عند وصول webhook متأخر.
- إن وصل حدث قديم بعد حدث أحدث: `GREATEST` يمنع رجوع الساعة للخلف.
- فشل لاحق **لا يمسح ولا يُرجع** `last_touch_at`.

### 4.6 غير مقروء
خارج v1؛ لا يُشتق من هذا العقد.

## 6) صلاحيات وكتابة ذرّية

| مسار | قدرة | مراجعة |
| --- | --- | --- |
| قراءة قوائم/تفاصيل | `read` | — |
| RPC يدوي: مرحلة/سبب/ملاحظة/موعد | `read` + `reply` | `lead_revision = expected` داخل المعاملة؛ رفض `subscribed` |
| تغيير المسؤول | `assign` عبر مسار التحكم | `control_revision`؛ RPC المرحلة **لا يكتب** `assigned_to` |

- فصل تام: `lead_revision` ≠ `control_revision`.
- الصلاحيات + الرؤية + المراجعة في نفس المعاملة قبل الكتابة.
- لا تجاوز عقد ACCESS؛ إن نقص مفتاح مطلوب يُوقف التنفيذ ويُراجع ACCESS — لا يُخترَع مسار بديل.

`/app/conversations`: تبويبات الكل | بانتظار رد الموظف | متابعة اليوم | متأخر | طلبات تجربة + عدّادات محادثات.  
لوحة: مرحلة (بدون subscribed) · سبب · ملاحظة · موعد (جدولة/إكمال/إلغاء/إعادة) · عرض المسؤول من `assigned_to` (تغييره عبر إسناد موجود).  
فشل تحميل ≠ قائمة فارغة. لا AI في v1.

## 8) معايير قبول

1. وحدة العدّ محادثة؛ نفس الهاتف بشركتين لا يُدمج.
2. RPC يرفض `subscribed`؛ UI لا يعرضه.
3. `scheduled` بلا تاريخ مرفوض؛ مكتمل/ملغى خارج القوائم النشطة مع بقاء التاريخ.
4. تعارض `lead_revision` / `control_revision` كلٌّ على مساره؛ لا overwrite.
5. `reply` لا يغيّر المسؤول؛ `assign` لا يمر عبر RPC المرحلة.
6. قائمة الانتظار بالاسم الصحيح؛ المساعد لا يُخرج؛ `failed` لا يُحتسب؛ فشل لاحق يعيد الإدراج إن تحقق §4.3.
7. UI لا يرسم `accepted` كـ`delivered`.
8. `last_touch_at` يتقدم بوقت الحدث فقط ولا يرجع للخلف.
9. تطابق عدّاد ↔ قائمة؛ UTC معلن عند غياب IANA.
10. لا مفاتيح ACCESS جديدة؛ لا سحابة/نشر في هذه الجولة.
