# مراجعة التسجيل والجلسة والصلاحيات — 8 أكتوبر 2026

## النتيجة الحالية

الكود المحلي يصحح رحلة الحساب، ويطبق انتهاء جلسة التطبيق بعد ساعتين دون نشاط، ويعزل عمليات الشركة المحددة. وظائف الجلسة وإصلاحات SQL اللازمة طُبقت على مشروع Supabase المطابق لإعدادات Velora، ثم تحققنا من وجودها وصلاحياتها. نُشرت النسخة المصححة على https://www.velorahelper.com عبر Vercel (deployment dpl_G1sEG3J44eM68HKBg6T5sSu7qWYZ)، ثم فُعّلت السياسة العامة على Data API/Storage وتحققنا أن enabled=true وأن الـ API hook و16 قيدًا موجودة. فحص المتصفح على الإنتاج نجح قبل التفعيل وبعده.

## رحلة الحساب

- هوية الإيميل تُقرأ من Auth وجلسة موثوقة، مستقلة عن فشل بيانات الشركة.
- INITIAL_SESSION فارغ في المتصفح لا يثبت تسجيل الخروج بعد Server Action؛ تتم مراجعة الخادم.
- أخطاء الشركة والصلاحيات لا تتحول تلقائيًا إلى Login.
- الإيميل المعلّق ووجهة next يبقيان أثناء التنقل والتأكيد. بيانات pending ليست دليل دخول ولا تحتوي كلمة مرور، وتنتهي بعد ساعتين.
- تأكيد البريد واستكمال الملف يحفظان وجهة العودة الداخلية المسموحة للدور.
- المسجل الذي يفتح login/signup يُعاد لمساره المسموح بدل بدء حساب آخر.
- الحساب الشخصي لا يعتمد على نجاح قراءة الشركة. الصفحة العامة تبقى قابلة للعرض عند تعطل الشركة.

## سياسة الساعتين

- كل جلسة مرتبطة بـ session_id وuser_id الفعليين في auth.sessions؛ جلسة جهاز آخر لا تمددها.
- الوقت من قاعدة البيانات، وتُقرأ الساعة بعد قفل صف الجلسة لتجنب خروج خاطئ عند تزامن النشاط والتحقق.
- فتح document فعلي أو إدخال/تمرير/عودة للنافذة يسجل نشاطًا. تحديث التوكن وقراءة الهوية وطلبات الخلفية لا تمدد المدة.
- check_app_session يرفض الجلسة المنتهية قبل السماح بتحديث النشاط؛ refresh token لا يعيدها إلى الحياة.
- اكتشاف الانتهاء من مؤقت النشاط أو تحديث الهوية يستخدم مسار خروج موحد، يحجب الصفحة المحمية ويعود للدخول مع next.
- المسودات المحفوظة حسب المستخدم تبقى؛ يتم تفريغ بيانات العرض الحالية فقط.
- نُشرت النسخة الجديدة ثم فُعّل ضابط Data API والقيود الإضافية على الجداول وStorage. ملف supabase/ops/activate_session_idle.sql يوثق خطوة التفعيل والتراجع.

## مصفوفة الوصول

| الهوية | الصفحات والعمليات |
|---|---|
| زائر | الرئيسية والباقات والصفحات القانونية والتسجيل/الدخول؛ لا بيانات شركة |
| بريد غير مؤكد | تأكيد البريد والهوية الشخصية المحدودة؛ لا عمليات شركة |
| عميل/مالك | الشركة المحددة التي يملكها، إعداداتها واشتراكها والمعرفة واختبار المساعد |
| موظف | محادثات شركته وفق المنح ونطاق التعيين، الحساب؛ المعرفة فقط بمنح read/write/delete الصريحة؛ لا دفع أو اختبار مساعد أو إعدادات مالك |
| أدمن المنصة | إدارة المنصة وفق صلاحياته؛ مساحة تشغيل الشركات لا تعني ملكيتها وتتطلب عضوية واختيار شركة |
| أدمن مفوض بعد ACCESS | الشركات والنطاقات والقدرات الممنوحة فقط؛ لا هوية حساب خارج نطاق إدارة الوصول ولا سجل تدقيق دون view_audit |

الهوية مرتبطة بالحساب، والدور مرتبط ببيانات العضوية والمنح؛ لا صلاحيات تُمنح بناءً على الإيميل المكتوب أو user_metadata أو واجهة المتصفح.

## إصلاحات SQL

- admin_list_company_conversations يتحقق من نطاق الشركة وقدرة قراءة المحادثة عند توفر ACCESS.
- access_get_user_snapshot يتحقق من علاقة الهدف بشركة مسموح إدارتها، ويحجب بيانات دور المنصة عن الأدمن المفوض.
- admin_get_company لا يعرض التدقيق دون قدرة view_audit بعد ACCESS.
- تحديث الشركة وقراءة/حفظ ربط واتساب يستخدمان RPCs تحمل company_id المختار والمتحقق منه، دون اختيار أول شركة ضمنيًا.
- RPCs القديمة ترفض حالة العضويات الملتبسة، وتبقى حالة إنشاء أول شركة متاحة للمالك الجديد.
- نموذج ACCESS المتقدم نفسه غير مطبق على القاعدة الحالية حسب فحص المخطط؛ إصلاح snapshot مشروط بوجود RPC. عند تطبيق هجرات ACCESS لاحقًا يجب إعادة تطبيق إصلاحات scope بعد أي تعريفات قديمة تستبدلها، والتحقق من الصلاحيات قبل تفعيل الأدوار المفوضة.
- لم تُغير أدوار أو منح أي حساب حقيقي، ولم تُقرأ قوائم الإيميلات أو كلمات المرور.

## أدلة التحقق

- TypeScript وESLint للملفات المعدلة.
- اختبارات src: 383 ناجحة، 18 متجاوزة تحتاج تجهيزات منفصلة. بناء الإنتاج على Vercel نجح، بما فيه TypeScript.
- PGlite: انتهاء الساعتين، عدم تجديد القراءة، رفض إعادة إحياء المنتهي، عزل الأجهزة، سحب الجلسة، منع RLS/Data API، صلاحيات RPC.
- PGlite للصلاحيات مع مخططين قبل/بعد ACCESS: اختيار شركة B دون تعديل A، التعليق، منع الالتباس، منح الموظف، نطاق الأدمن، خصوصية snapshot وسجل التدقيق.
- متصفح: حفظ pending email بعد إعادة الدخول لصفحة التأكيد، next للاشتراك، ومنع الزائر من رابط الإعدادات؛ بلا أخطاء JavaScript أو hydration. لا إرسال بريد ولا إنشاء حساب حقيقي ضمن الاختبار.
- فحص السحابة: session RPC وselected-company/WhatsApp RPCs موجودة؛ authenticated لا يقرأ جدول الجلسات الخاص؛ anonymous مرفوض؛ 16 قيد جلسة موجودًا؛ database enforcement=true.
- لا توجد تجربة دخول حقيقية لكل حساب على الموقع المنشور؛ اختبارات الأدوار والجلسة تمت ببيانات مصطنعة؛ لم تُستخدم كلمات مرور أو حسابات عملاء حقيقية. الإغلاق العام نشط حسب التحقق من القاعدة، ولم ننتظر ساعتين فعليتين لاختبار كل حساب.

## تحديث النشر

- الدخول من المتصفح يستخدم Auth SDK لتنسيق الكوكيز ومزامنة تغييرات الحساب بين التبويبات؛ التوجيه والصلاحيات من الخادم.
- عند تغيير الحساب أو الشركة يعاد تحميل بيانات مساحة العمل بدل إبقاء واجهة حساب سابق.

- لا يوجد حذف لمسودات الشركات عند انتهاء الجلسة؛ البديل الذي يحافظ عليها طُبق بعد رفض مراجعة الموافقة التلقائية للحذف.
