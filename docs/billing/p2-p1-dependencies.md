# P2 activation audit: dependencies on P1

Audit date: 2026-10-08. Isolated branch: `codex/p2-billing-readiness`, base `afe2e298bfb4ef16414b83fb7077a2ca2f1e5c62`. This report reviews the local migration sources and Billing code. It does not establish which migrations are installed in a cloud database. No SQL, provider request, financial transaction, migration, deployment, or secret inspection was performed by this audit.

The P2 application changes improve evidence validation and retry handling. They do not establish live subscription activation. Database, authentication, and RLS changes are outside this work package; the requirements below are **P1 DEPENDENCIES**.

## Existing database guarantees

- Tenant consistency has composite foreign keys for attempts, events, subscriptions, orders, and grants, plus an order/attempt/company grant trigger: [foundation migration](../../supabase/migrations/20261006180000_vel_billing_foundation_01.sql), lines 108–112, 142–160, 231–268, and 419–500. The latest settlement core independently compares company, attempt, order, account, environment, amount, currency, and reference at [lock-order migration](../../supabase/migrations/20261006310000_vel_billing_lock_order_and_unknown_fix_03.sql), lines 375–387.
- Exact provider observations are unique by provider/account/environment/transaction/status/observation key. Grants are unique by scoped transaction, attempt, and purchase order. A second collection for one order becomes `duplicate_collection_review`, without extending the paid period: foundation lines 146–152 and 261–268; latest core lines 399–435 and 548–587.
- The latest core locks company, subscription, order, and attempt before applying a grant, and updates the grant, subscription, attempt, order, and outcome in one function transaction: lock-order migration lines 333–368 and 602–717. Purchase persistence takes company/subscription/order locks and rechecks initial/renew eligibility: lines 791–862.
- Published/retired financial plan fields and locked order financial/identity fields are immutable on update: [atomic migration](../../supabase/migrations/20261006210000_vel_billing_atomic_settlement_01.sql), `private.billing_plan_versions_immutability` at line 158 and `private.billing_orders_immutability` at line 207. Renewal arithmetic adds calendar periods to `max(server_now, paid_through)`; [period model](../../src/lib/billing/period.ts), lines 72–105, matches the SQL helper.
- Browser roles have billing table privileges revoked and RLS enabled. The HMAC settlement RPC is restricted to `service_role`; authenticated customer/admin projections perform explicit session and owner checks: foundation lines 505–519; [HMAC RPC migration](../../supabase/migrations/20261006230000_vel_paymob_test_wiring_01.sql), lines 31–40 and 95–104; [UI adapter migration](../../supabase/migrations/20261008050000_vel_billing_ui_adapter.sql), lines 18–43 and 164–237.

These are source-level guarantees, not a report of executed database verification.

## P1 DEPENDENCIES

### D1 — Live settlement and live operational entitlement

**Severity: launch blocker.** `public.billing_settle_paymob_hmac_verified` rejects live at HMAC migration lines 57–59. The latest `private.billing_settle_payment_core` requires `provider_environment='test'` at lock-order migration lines 318–327 and 389–392. The older `public.billing_settle_verified_payment` remains a disabled entry and rejects synthetic evidence: [atomic fix migration](../../supabase/migrations/20261006220000_vel_billing_atomic_settlement_fix_01.sql), lines 599–681. A test RPC returning `granted` cannot establish live activation.

**Acceptance:** implement an explicitly reviewed, service-only live settlement contract with authenticated processor evidence and pinned live merchant/integration/environment binding. Preserve amount/currency/order/tenant checks, atomicity, duplicate handling, and synthetic-evidence rejection. Connect live entitlement evaluation to durable live collection evidence and server expiry checks; [readCompanyEntitlement](../../src/lib/billing/entitlement.ts), lines 28–38, currently remains fail-closed. Verify real database state and privileges in the separately authorized P1 environment. Customer/WhatsApp rollout stays a separate activation step.

### D2 — Test/live subscription state contamination

**Severity: launch blocker before test and live coexist.** Events and grants are environment-scoped, but `billing_subscriptions` has one row per company without an environment field: foundation lines 178–196. Test settlement writes that row's `paid_through`, `plan_version_id`, `status`, and cancel flag: latest core lines 680–687. Purchase eligibility reads the same paid period at lines 812–839. Test paid time can therefore block a subsequent live initial purchase or become the remainder used by a future live renewal. The existing live-only journey projection filters grants/orders at UI adapter lines 176–182, but it does not isolate mutation or purchase state. [loadOwnerBillingSubscription](../../src/lib/billing/wiring/subscription-read.ts), lines 14–24, also treats the shared future paid period as active.

**Acceptance:** either separate subscription state by environment with corresponding foreign keys/uniqueness, or maintain a canonical live-only operational subscription derived and mutated exclusively from live grants. Make all purchase, renewal, cancellation, usage, and operational entitlement paths use the chosen authoritative state. Test grants and test pending orders must neither activate live service nor block/live-extend a paid purchase. Verify both environments on the same company, including renewals and cancel flags, using database tests.

### D3 — Atomic plan publication, expiry, and snapshot validation

**Severity: launch blocker for authoritative offer eligibility.** The application reads a plan before calling a separate mutation: [createBillingOrderAction](../../src/lib/billing/wiring/order-actions.ts), lines 150–169 and 317–335. [decideCreateBillingOrder](../../src/lib/billing/wiring/order-create.ts), lines 122–127, checks the supplied snapshot's publication status. The latest database purchase function inserts caller-supplied version/amount/currency/period at lock-order migration lines 924–965 without loading and locking the catalog version or checking plan activity/publication/catalog consistency. Publishing a replacement can retire the previously read version before purchase persistence. The plan-version schema has no validity/expiry field: foundation lines 29–42. No order checkout expiry is defined either.

**Acceptance:** define offer validity and checkout expiry policy in P1. Within the purchase transaction, load/lock the selected plan and version, verify current publication, plan activity, product/plan relationship and server-time validity, and derive the financial/period snapshot from that row. Reject expired, draft, retired, or unpublished new purchases without creating an order/attempt. Preserve already locked legitimate order snapshots across later catalog publication, according to the explicit checkout-expiry policy. Add database tests for publication-versus-purchase races, mismatched financial inputs, expired offers/orders, and preservation of historical grants.

### D4 — Automatic failure/cancellation/refund reconciliation and signed lifecycle ordering

**Severity: launch blocker for a complete payment lifecycle.** [processStoredPaymobEvent](../../src/lib/billing/wiring/event-process.ts), lines 64–68, skips pending and every non-success status. [processOwnerOrderEvents](../../src/lib/billing/wiring/order-event-processing.ts) originally loads only stored success events. The SQL event enum only distinguishes `pending/success/failed/other`: foundation lines 131–139. `private.billing_confirm_payment_attempt_failed` and `private.billing_open_payment_attempt_after_confirmed_failed` do bind failure evidence and prevent stale failure/retry when durable success exists: [failure-evidence migration](../../supabase/migrations/20261006300000_vel_paymob_failure_evidence_fix_05.sql), lines 73–82, 94–174, and 252–293. Those functions do not provide automatic webhook failure reconciliation or a refund/void/cancel reversal workflow. The latest settlement core validates success evidence but does not prove a complete signed lifecycle or inspect authoritative later terminal/reversal observations before granting.

**Acceptance:** persist canonical, verifiable lifecycle evidence and apply an explicit transition/reversal policy under the settlement transaction locks. Distinguish payment collection from authorization, capture actions, child transactions, voids, refunds, and cancelled orders. Establish processor-supported event ordering or authenticated reconciliation rather than relying on arrival time or an array's last item. Drive evidenced failed-attempt confirmation and safe retry from the durable queue; preserve unknown/pending outcomes and valid existing paid periods. A stale success must not grant after authoritative cancellation/refund/void, and replay must not reactivate a reversed collection. Define refund entitlement handling and review outcomes explicitly; do not invent a refund policy in P2.

**Historical evidence:** existing success rows may have been written by earlier callback classification or lack the full lifecycle flags. P2 guards the actual persisted-event loaders and requires reconciliation for incomplete legacy rows; [stored-evidence loader tests](../../src/lib/billing/wiring/p2-stored-evidence.test.ts) exercise those actual loaders with database/RPC doubles. P1 must audit historical records before trusting or activating them, and enforce evidence completeness/order within the atomic RPC. The generic [process runner](../../src/lib/billing/wiring/process-runner.ts), lines 13–35, accepts a caller-supplied event loader; no production loader was found for it in this audit. Its dependency injection does not itself establish trusted evidence.

### D5 — Durable provider-order binding uniqueness and immutability

**Severity: launch blocker for deterministic merchant/environment/tenant binding.** `billing_payment_attempts.provider_order_id` and `provider_intention_id` are plain nullable text without a scoped unique provider binding: foundation lines 104–112. [billing_complete_test_checkout](../../supabase/migrations/20261007010000_vel_paymob_test_checkout.sql), lines 78–94, binds the supplied provider order to an attempt but does not enforce uniqueness across provider/account/environment. P2 hardens [findOrderByProviderOrderId](../../src/lib/billing/wiring/store.ts) to reject ambiguous results and invalid persisted data instead of selecting the newest tenant. That application rejection does not prevent conflicting database bindings.

**Acceptance:** create a canonical provider/account/environment/order identity mapping with a database uniqueness arbiter and immutable binding after submission. Bind the provider transaction to that persisted attempt/order scope. Make ambiguous, cross-account, cross-environment, or reassigned identities fail closed in both lookup and settlement. Preserve tenant composite foreign keys and service-only privileges. Verify duplicate binding attempts and simultaneous cross-tenant/environment writes in the database.

## Required P1 database verification

Use a separately authorized, disposable database with the full latest migration chronology. Exercise real transactions on independent connections: identical and distinct successful collections for one order; simultaneous different orders for one subscription; purchase-versus-settlement and catalog-publication-versus-purchase; wrong tenant/account/environment binding; rollback after intermediate writes; stale pending/failed/success/refund/cancel permutations; test/live coexistence; expiry and calendar renewal. Assert committed row counts, grant/outcome identity, exactly-once paid-period extension, immutable snapshots, no partial writes, and denied anonymous/authenticated direct writes. Application mocks must remain labeled as application verification.
