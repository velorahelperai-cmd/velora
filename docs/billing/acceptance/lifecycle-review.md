The signed `is_refunded` field proves the provider signed that state. It does **not** by itself prove whether a refund was partial/full, the refund amount accumulated so far, or the original collection behind a child transaction. The signed `amount_cents` and `has_parent_transaction` are retained, and their financial interpretation stays unconfirmed. No refund, grace period, service suspension, renewal cancellation or OMR conversion policy is invented here.

Payment-request cancellation and cancellation of future subscription renewal are separate operations. The reversal helper rejects `cancelled`; a failed/pending payment observation does not cancel a subscription. Verified void and refund evidence have separate review reasons. Evidence/history is not deleted or rewritten.

Owner decisions still required before staging acceptance: adopt/revise the payment deadline; define late collections; define the service effect of a verified complete reversal, partial refund and ambiguous child transaction; define an authorized reconciliation/review workflow. No cloud SQL or migration application is authorized by these notes.

`deadline_policy_approved` is a database field, not a Webhook/browser assertion. It defaults false and is not populated from evidence. Positive Live PostgreSQL fixtures deliberately insert true only to exercise the approved branch with synthetic data; those tests are not an owner policy approval. Existing proven grants can still replay idempotently after expiry; newer purchases are not revoked by this guard.

The forward correction preserves the working locked grant implementation behind the new gate. Its normalized source hash is pinned to the reviewed P1/integration commit before renaming. A different installed function body aborts the migration with `SETTLEMENT_CORE_VERSION_REQUIRES_REVIEW`; it is not silently copied or treated as verified. This narrow guard does not replace a complete authorized cloud catalog/privilege/constraint check.
