# Internal team foundation — local review checkpoint

This forward migration and server contracts are **not installed, published or exposed in a live route**. Production currently lacks these team relations/RPCs. Keep schema and application release synchronized after separate owner approval; a local commit does not close the release gate.

The owner creates/updates teams, enrolls/disables existing verified employees and transfers a selected internal membership atomically. No invitations or Auth accounts are created. An existing delegated admin may manage multiple teams. Roster access requires the current persisted active delegated-admin role, verified current Auth identity, the owner-set team manager pointer, and active same-team membership. That pointer and membership persist the specific team scope; company capabilities do not provide team scope. Other employees see only their own plural membership statuses and eligible manager summaries. Owner-controlled manager replacement immediately removes the previous manager's roster access; disabling/transferring the current manager first requires replacement. Disabling a team denies its current team metadata/roster while retaining the caller's own membership history. Platform role disable revokes all delegated rosters. History stays preserved.

Multiple independently revocable active memberships are allowed. A transfer disables only the selected source membership and activates an absent/inactive destination; an already active destination conflicts. Unrelated memberships and company grants remain unchanged. Specialty is owner-set directory text, never authority. Team membership never promotes platform admins or grants company, billing or finance access. Existing `platform_admin_scopes`, company memberships and `company_member_grants.manager_user_id` remain separate and unchanged. Active team managers have no employee reporting edge in another active team, preventing self/cyclic manager relationships. Replacement atomically enrolls/reactivates the new eligible manager; if the old manager still manages another active team, only the replaced-team membership is disabled. Promotion or reactivation that would create an employee edge for an active manager returns INVALID_MEMBER before writing. Auth deletion is restricted while directory/history/operation records refer to the user; account cleanup requires a separately reviewed lifecycle policy.

Public RPCs: `platform_team_read_self()`, `platform_team_read_directory(uuid,uuid,integer,integer,text,jsonb)`, `platform_team_preview_transfer(jsonb)`, `platform_team_mutate(jsonb)`. Self reads return sorted caller-only plural memberships; denied entries hide team and manager metadata. Directory search is a bounded literal case-insensitive substring of team name or authorized roster name/specialty; rows, count and cursor share the same scope/filter. Owner mutation operations are `create`, `update`, `set_member`, `transfer`. Each carries expected revisions, stable operation UUID and a trimmed 2–240-character reason. Optional set_member specialty is trimmed and bounded to 120 characters; omission preserves it. Transfers require source/destination team and membership revisions, including revision 0 for an absent destination row. A preview is a revision-bound read, not a reservation; commit repeats all checks under locks. Before returning a successful preview, a VOLATILE read-only helper freshly checks actor/session, persisted owner role, destination-manager eligibility and all four captured team/member revisions. Preview works in a read-only transaction and writes no audit/outcome.

Cursor row ID/revision is accompanied by actor, team-or-list context, trimmed search and a captured scope fingerprint. The fingerprint is MD5 of canonical JSON containing owner mode and the selected team's revision for a roster, or all currently authorized team IDs/revisions for the team list. Changes outside the last cursor row invalidate pagination with CONFLICT. Parser/decoder preserve context, and SQL validates it under independently checked current authorization. Actor/team/search mismatch or an unbound legacy cursor is INVALID_INPUT. This is ordinary unsigned navigation state, not a credential, grant or reservation; changing it cannot bypass current role/scope checks. A fresh first page starts again without a cursor. Terminal directory checks compare the entire current revision map, including added/removed scope.

All reads validate a verified stored Auth user, matching stored session, JWT expiry, stored session deadline and an unexpired two-hour activity lease using the current clock. Mutations serialize under one transaction advisory lock, lock team IDs/member keys in deterministic order, then acquire ordered target Auth and actor Auth/session/activity/admin locks with NOWAIT. Authority and expiry are checked again after all blocking locks and before writing; lock contention returns UNAVAILABLE without changes. This avoids cycles with session pre-request work. Exact retries return the private confirmed outcome after current owner authorization; a changed payload conflicts. Mutation, existing audit writer and successful outcome commit together. Audit failures roll back all changes. Confirmed results include persisted row projections so a failed subsequent read cannot replace write success. Server mutation receipts include actorUserId and accessNeedsRecheck; a failed optional session recheck preserves the confirmed receipt without granting current access. A known different current account still rejects the result. Future UI callers must bind requests/results to the current account and request generation, recheck access before displaying protected data, and keep a stable operation UUID for uncertain-response retries.

Supported self/directory RPCs perform terminal current-authority and captured team/member revision checks after materialization. A membership/team change during a pending response yields CONFLICT; a lost manager role or captured manager eligibility yields FORBIDDEN. A fresh self read can show denied own status without restoring access. Direct authenticated team-table writes and all access to the private outcome ledger are denied. Direct-table RLS allows owner reads, eligible scoped manager rosters and caller-only membership history with current team summaries; it retains ordinary statement-snapshot semantics and does not establish the RPC's pending-response guarantee for arbitrary direct SELECT. Cursor IDs/revisions must belong to the currently authorized scope. No schema `USAGE` grant to `authenticated` is added. Security-definer implementations are private; public wrappers use an empty search path and narrowly granted authenticated execution.

## Approval, release and recovery

Before any release: independent source/SQL review; approve this exact migration SHA-256; rerun read-only production preflight; have the authorized installer apply the SQL transaction; verify new catalog ACLs/RLS and synthetic role tests in an approved environment; authorize the corresponding tested main push/deployment; verify exact deployment and desktop/main synchronization. No live team navigation should appear before all schema/code/access checks pass.

If installation fails, its transaction rolls back. If SQL is installed but publication fails, existing product paths are unchanged and no UI imports these actions; keep the feature unexposed and repair forward. If a later access defect appears, an authorized installer can revoke authenticated EXECUTE on the four new RPCs and authenticated SELECT on the two new tables to contain access, then review a forward repair. Do not delete existing data, undo unrelated memberships/grants, configure new persistent access or silently seed permissions. An uncertain successful mutation is recovered with the original actor/operation UUID and exact payload after session recovery, producing no duplicate audit/write.
