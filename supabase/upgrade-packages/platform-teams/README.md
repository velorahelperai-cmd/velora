# Internal team foundation — local review checkpoint

This forward migration and server contracts are **not installed, published or exposed in a live route**. Production currently lacks these team relations/RPCs. Keep schema and application release synchronized after separate owner approval; a local commit does not close the release gate.

The owner creates/updates teams, enrolls/disables existing verified employees and transfers one active internal membership atomically. No invitations or Auth accounts are created. A manager derives from the team's current manager pointer plus active same-team membership, reads only that roster, and has no reporting edge. Other employees see only their membership and manager summary. The flat model prevents reporting cycles/self-management. Owner-controlled manager replacement immediately removes the previous manager's roster access; disabling/transferring the current manager first requires replacement. Disabling a team removes current member/manager reads. History stays preserved.

One active internal team per user and manager authority independent of platform-admin role are the implementation's explicit design choices, pending parent confirmation. Team membership never promotes platform admins or grants company, billing or finance access. Existing `platform_admin_scopes`, company memberships and `company_member_grants.manager_user_id` remain separate and unchanged. A platform-admin role change cannot create a reporting relationship. Auth deletion is restricted while directory/history/operation records refer to the user; account cleanup requires a separately reviewed lifecycle policy.

Public RPCs: `platform_team_read_self()`, `platform_team_read_directory(uuid,uuid,integer,integer)`, `platform_team_preview_transfer(jsonb)`, `platform_team_mutate(jsonb)`. Owner mutation operations are `create`, `update`, `set_member`, `transfer`. Each carries expected revisions, stable operation UUID and a trimmed 2–240-character reason. Transfers require source/destination team and membership revisions, including revision 0 for an absent destination row. A preview is a revision-bound read, not a reservation; commit repeats all checks under locks.

All reads validate a verified stored Auth user, matching stored session, JWT expiry, stored session deadline and an unexpired two-hour activity lease using the current clock. Mutations serialize under one transaction advisory lock, lock team IDs/member keys in deterministic order, then acquire ordered target Auth and actor Auth/session/activity/admin locks with NOWAIT. Authority and expiry are checked again after all blocking locks and before writing; lock contention returns UNAVAILABLE without changes. This avoids cycles with session pre-request work. Exact retries return the private confirmed outcome after current owner authorization; a changed payload conflicts. Mutation, existing audit writer and successful outcome commit together. Audit failures roll back all changes. Confirmed results include persisted row projections so a failed subsequent read cannot replace write success. Server mutation receipts include actorUserId and accessNeedsRecheck; a failed optional session recheck preserves the confirmed receipt without granting current access. A known different current account still rejects the result. Future UI callers must bind requests/results to the current account and request generation, recheck access before displaying protected data, and keep a stable operation UUID for uncertain-response retries.

Direct authenticated team-table writes and all access to the private outcome ledger are denied. RLS permits only owner reads, the manager's current roster, or an employee's current row/team summary. Cursor IDs/revisions must belong to the currently authorized scope; counts and cursor lookups share the same scope. No schema `USAGE` grant to `authenticated` is added. Security-definer implementations are private; public wrappers execute only these guarded functions with an empty search path and narrowly granted authenticated execution.

## Compatibility and verification

Run `preflight.readonly.sql` against the selected production project to inspect catalog metadata only. It pins the observed owner/session/audit definitions, required columns, RLS and absence of new objects. It returns no user/customer rows, secrets or sessions. The installer independently checks trusted namespace/function owners and security configuration; it creates new objects atomically and refuses pre-existing table/function names. Do not bypass a changed/missing dependency or repeat this forward installer on an already installed package.

Native tests use only synthetic users and fixture dependencies in a no-network, no-port, no-log PostgreSQL container with tmpfs storage. Each run creates a fresh uniquely named fixture database. Synthetic Auth/session/activity tables use the checked-in existing idle-session predicate, owner predicate and audit writer. New terminal checks are exercised against real session activity expiry while waiting for hierarchy and team locks. This proves the new SQL behavior; it does not claim a full production-schema replay or authenticated PostgREST/browser acceptance. Local PostgreSQL is 17.6; production catalog reports 17.11.

```bash
docker run -d --name velora-platform-teams-local --label velora.task=platform-teams --network none --log-driver none --tmpfs /var/lib/postgresql/data:rw --tmpfs /var/run/postgresql:rw -e POSTGRES_HOST_AUTH_METHOD=trust postgres:17.6-alpine
node scripts/platform-teams/cases.mjs
npx vitest run src/lib/platform-teams/contracts.test.ts src/lib/platform-teams/actions.test.ts
```

The harness verifies container identity/configuration and then uses its immutable container ID, never a connection URL or real credentials. Do not replace its bootstrap fixture with production data.

## Approval, release and recovery

Before any release: independent source/SQL review; approve this exact migration SHA-256; rerun read-only production preflight; have the authorized installer apply the SQL transaction; verify new catalog ACLs/RLS and synthetic role tests in an approved environment; authorize the corresponding tested main push/deployment; verify exact deployment and desktop/main synchronization. No live team navigation should appear before all schema/code/access checks pass.

If installation fails, its transaction rolls back. If SQL is installed but publication fails, existing product paths are unchanged and no UI imports these actions; keep the feature unexposed and repair forward. If a later access defect appears, an authorized installer can revoke authenticated EXECUTE on the four new RPCs and authenticated SELECT on the two new tables to contain access, then review a forward repair. Do not delete existing data, undo unrelated memberships/grants, configure new persistent access or silently seed permissions. An uncertain successful mutation is recovered with the original actor/operation UUID and exact payload after session recovery, producing no duplicate audit/write.
