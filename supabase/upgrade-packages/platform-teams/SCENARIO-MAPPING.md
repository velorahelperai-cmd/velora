## Model correction and code rationale

The r1 checkpoint and archive remain preserved. R2 removes the global active-user membership uniqueness constraint while retaining `(team_id,user_id)` identity. The owner-controlled team manager pointer is the persisted per-team scope; membership alone cannot grant roster authority. `private.platform_team_manager_eligible` additionally requires the current stored delegated/active platform role and current verified, nondeleted, nonbanned Auth user. This implements approved multi-team admin responsibility without modifying company capability semantics.

Independent revocation and transfer modify only selected memberships. An active destination conflicts. The SQL consistency invariant allows a manager to be root of several teams, but rejects an active employee edge in another active team, preventing cycles. Replacement atomically enrolls the eligible manager and only removes an old manager's replaced-team employee edge when that person still manages elsewhere.

Supported read RPCs capture team/member revisions with their rows and recheck using a VOLATILE current-authority helper after materialization. Revision changes produce CONFLICT; eligibility/scope loss produces FORBIDDEN. Captured manager summaries also recheck current manager eligibility. Fresh self reads retain caller-only denied history and hide team/manager metadata. This is a server read guarantee at its terminal check, not browser delivery cancellation or arbitrary direct-table transaction linearizability.

Critical SQL excerpts (authoritative complete text is 10-teams.review.sql):

```sql
-- Manager role predicate includes persisted platform role and Auth eligibility.
-- Per-team scope additionally requires owner-set pointer and active same-team member.
-- No global active-user membership uniqueness remains.
if m.user_id is null or m.revision is distinct from (entry->'membership'->>'revision')::integer
 or t.revision is distinct from (p_revisions->>t.id::text)::integer
then raise exception 'CONFLICT'using errcode='42501';end if;
if entry->'manager'<>'null'::jsonb
 and not private.platform_team_manager_eligible(t.manager_user_id)
then raise exception 'FORBIDDEN'using errcode='42501';end if;
```

Critical server contract excerpt: `TeamSelf` contains a plural `memberships: Array<...>`; its strict decoder verifies each entry belongs to the requested actor, is uniquely sorted by team, and denied entries carry `team:null` and `manager:null`. The actor-bound confirmed mutation receipt is retained after optional post-write identity failure, with `accessNeedsRecheck:true`, and rejects a known different current account. Complete contracts/actions are separate small review files.

## R3 review corrections and runtime provenance

R2 `{id,revision}` cursor acceptance across account/team boundaries was a proven parser mismatch, not demonstrated unauthorized access. Native regressions additionally reproduced reuse across two authorized teams sharing the same member revision, and stale pagination after another membership changed. R3 coordinates `TeamCursor` actor/team/search/scopeRevision, decoder context checks, authenticated RPC `p_cursor_context`, SQL generation and validation. The scope fingerprint includes owner mode plus the roster team revision or full authorized team ID/revision map. It is unsigned navigation state; current authorization is independently enforced before cursor checks and again at the terminal read check.

R2 paused preview regressions reproduced success after owner/destination-manager disable and after each captured revision changed. R3's read-only VOLATILE terminal helper checks current actor/session/owner, destination-manager eligibility and all four revisions before successful projections return. The synthetic pause wraps the original private materializer and blocks just before the public terminal boundary, leaving real table triggers and original snapshot reads intact. All audit/outcome counts remain unchanged by preview.

Production metadata-only reads on 2026-10-11 confirm the exact owner/session/audit pins remain current and required catalog columns/RLS/new-object absence are compatible. Desktop's blocked 78-migration G03 replay and successful 72-prefix synthetic Auth/HTTP sessions are separate evidence; no R2 team installer/assertions completed. The inspected checked-in owner source (`e76d5…`) and production predicate differ only in formatting; desktop-reported runtime `8e066…` was not supplied as a definition and is not independently semantically verified. R3 preserves exact production hash guards, supplies guarded local-only sanitized function definitions with provenance, and uses them in the miniature fixture. That is dependency alignment, not complete canonical-schema/Auth/PostgREST acceptance. Desktop must execute the R3 installer/assertions on its isolated production-equivalent baseline.
