# P3 dependencies and first real test gate

**Ready for First Live API Test: NO.** The application changes are verified offline. The installed database functions, their execution permissions, active owner/session checks, actual budget state, provider keys and account/model availability have not been verified against the deployed environment in P3. No provider call, SQL execution, migration application or deployment was performed. A migration file is source evidence, not proof that its contents are installed.

This review is based on [runtime persistence](runtime/store.ts), [execution](runtime/execute.ts), [provider integration](runtime/provider.ts), [economics](runtime/economics.ts), [owner actions](runtime/admin-actions.ts) and the existing [runtime foundation SQL](../../../supabase/migrations/20261008040000_vel_ai_runtime_foundation.sql). P3 did not modify that SQL or Auth/RLS.

## Dependencies needed before the owner's first real trial

1. **Installed persistence and authorization contract.** P1 must verify `ai_reserve_attempt`, `ai_start_attempt`, `ai_settle_attempt`, `ai_admin_snapshot` and `ai_reconcile_attempt`, their exact signatures, service-role-only execution, required table grants, and the corresponding owner/session authorization. The source reserve/start functions require an active platform owner and a nonexpired session with activity in the preceding two hours. These guarantees are unverified in the installed database. A missing/malformed RPC result blocks local dispatch; it must not be replaced with an in-memory success.

2. **One global lifetime administrative budget of 1 OMR.** The source defines a unique `admin_test` budget with `company_id IS NULL`, seeded to **1000 baisa**, and reserves against that row for every owner/company/model. Administrative reservation ignores the monthly `period_start` filter, so this is a lifetime shared cap rather than a fresh allowance per tenant, owner, model or month. P1 must verify the actual singleton's `limit_baisa`, `spent_baisa`, `held_baisa` and `enabled` state. Preserve previous spend/holds. Do not reset, duplicate or increase this allowance to make a test pass. The source permits any nonnegative `limit_baisa`; it does not independently constrain an administrative account to at most 1000. P1 should enforce the approved ceiling and the policy for authorized budget changes.

3. **Atomic concurrency proof.** In source, reserve locks the budget row before checking `spent + held + reservation <= limit`; settlement takes the same budget lock before locking the attempt. A unique `(execution_id, attempt)` rejects a duplicate execution attempt, and start conditionally changes `reserved` to `running`. This is a useful existing production path. Mock tests cannot prove installed locking, concurrent authorization, grants, transaction rollback or duplicate execution behavior. P1 must verify these database guarantees with its authorized database test workflow. Legacy `checkCompanyAIBudget` is explicitly an offline snapshot and cannot enforce a concurrent paid allowance.

4. **Valid cost upper bounds.** The application reserves before dispatch, has bounded output and test-cost inputs, disables SDK retries, and stops after an uncertain response. Runtime reservation uses a conservative prompt estimate and reserves Gemini's full output/thinking window because a small visible output limit is not an independent thought-token ceiling. P1 must retain this policy. Verify the account's selected tariff, model identifier, supported settings and actual usage mapping before a real test. The source settlement can record actual cost above the reservation/limit and then disable the account; disabling cannot undo already incurred expense. The strict 1 OMR promise therefore also depends on the reservation being an actual upper bound for the configured API request.

5. **Reconciliation of retained holds.** Source `ai_reconcile_attempt` exists for operator/provider-evidence reconciliation of `uncertain`, `reserved` and `running` attempts; recent reserved/running attempts require at least five minutes before reconciliation. The application runtime does not currently expose a consumer for this function. A timeout, crash or unsuccessful settlement can leave money held indefinitely. P1 needs a service-only recovery operation with actual provider evidence, idempotent settlement and an audit trail. Do not automatically release a hold or repeat a request whose execution/billing status is unknown.

6. **Administrative trial authorization remains separate from customer rollout.** The reusable path is `runAdminAITrial` -> `executeRealAnswer` -> reserve/start -> provider -> settle. The owner action derives actor/session from verified server context; caller-provided company/model/execution identifiers do not replace that authorization. The prepared [connectivity tool](diagnostics/ping-test.ts) creates independent pinned trials with a fixed synthetic prompt, **128 output tokens** and a **250 baisa reservation ceiling**, each consuming the same lifetime 1000 baisa budget. Its `executeConfirmed: false` default causes no database/provider work; confirmation still passes through owner/session authorization. Optional owner-action caps are forwarded to runtime validation before reservation. This confirmation is a deliberate owner action, not permission for this agent to run the tool. The requested first test remains unexecuted; a new explicit owner request is required for any agent-run paid verification.

## Durable telemetry contract to complete with P1

The existing source ledger stores company, actor/session, requested model/provider, execution/attempt, reservation, cost, prompt/output/cached/reasoning counts, provider reference, latency, pricing snapshot/version and timestamps. Each fallback uses its own persisted attempt. OpenAI reasoning is a subset of output and must not be charged a second time; cached reads and cache writes must remain separate input categories. The P3 application validates all required numeric usage fields, token sums and subset relationships before pricing. It retains provider-returned model/response metadata in attempt traces when supplied, and an explicitly mismatched model keeps cost uncertain and the reservation held instead of being priced as the requested model.

The current **durable** contract is incomplete for the requested diagnostics:

- Application traces now retain separate `actualModelId`, `responseId` and `requestId` fields, but P1's ledger has only requested `model_id` and one `request_id` column. The current persistence RPC drops the separate actual-model and response identifiers. Missing optional model metadata is tolerated for legacy compatibility, so an absent actual model must not be presented as a provider-confirmed model. A returned model mismatch must not silently be accounted as the requested model.
- `RealTokenUsage` includes cache writes, but the existing `ai_settle_attempt`/`ai_reconcile_attempt` SQL does not store `cacheWriteTokens`; the table has no cache-write column. Actual cache-write cost can be calculated locally while its explanatory token count is lost in durable records.
- `RealTokenUsage` now retains `totalTokens` and local parsing validates `total = input + output`, cached/cache-write and reasoning subsets, safe nonnegative token values and complete required usage before pricing. There is still no durable total-token column or database constraint enforcing those relationships, nonnegative token/latency values, or a valid provider/model pairing. P1 must add the authoritative storage/validation contract.
- The SQL accepts server-supplied pricing snapshots/costs. P1 must keep pricing/version evidence associated with the exact attempt and review consistency between reservation, actual usage and settlement. Cost uncertainty must remain visible rather than being turned into a fabricated zero.

These schema/RPC additions are intentionally documented rather than implemented in P3. Optional offline `AnswerUsage`/attempt telemetry does not create corresponding database columns.

## Dependencies for customer production activation

- **Subscription and quota enforcement:** the source `company_live` reservation checks company-owner membership and company suspension, but does not verify a paid active subscription, product entitlement or message/token quota. P1 must enforce these atomically with budget reservation before customer activation. P3 keeps `company_live`, Live Answering and WhatsApp activation disabled.
- **Approved Knowledge and tenant proof:** the existing company-scoped context loader and citation revalidation remain in place. Low-level chunks do not contain a tenant/approval proof; a valid chunk shape is not proof of ownership or approval. Customer callers must use the trusted scoped context path and recheck approval before delivery.
- **Sensitive business actions:** model selection does not prove that a refund, payment, account change or human escalation occurred. The router has an independent conservative sensitive-request gate, and model override cannot remove it. Complete semantic/action authorization and execution evidence belong to a trusted business-action verifier/human workflow. No caller-supplied boolean should bypass it.
- **Uncertain failures and fallback:** a definite permitted rejection can authorize an eligible fallback; timeout, transport failure, empty/incomplete billable response and usage-limit exhaustion cannot authorize a second paid request. Real execution now reuses the router's eligible-model plan, keeps capability floors and explicit-model pinning, and excludes HTTP 429 from its fallback whitelist. Preserve these controls when integrating other callers.
